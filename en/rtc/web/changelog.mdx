### Recent updates

### v0.7.7 - 2026-11-25

+ **New per-user playback volume `setRemoteUserVolume` / `getRemoteUserVolume`**: adjusts how loud you hear a given user locally (0 to 1, with a ramp and no popping). It applies to both the user's microphone and screen-sharing audio, audio tracks the user publishes later pick it up automatically, and it's cleared when the user leaves the channel. It only affects you, not other members. Per-user adjustment isn't possible in channels with server-side mixing; the call returns `false`. See [SRTC · setRemoteUserVolume](/en/rtc/web/api-reference/SRTC#setremoteuservolume) for usage
+ **New audio clip playback `playAudioClip`**: plays an audio clip (ArrayBuffer / Blob / URL) into your local audio output. While the mixed audio track is playing, the clip comes out of the same speaker as remote voices. The returned handle gives the duration, lets you stop at any time, and lets you wait for it to finish. Only you hear it; it isn't published to the channel, and it stops automatically when you leave the channel. Suitable for playing interpretation audio for simultaneous interpretation, notification sounds, and similar cases. See [SRTC · playAudioClip](/en/rtc/web/api-reference/SRTC#playaudioclip) for usage and [Audio clip types](/en/rtc/web/types#audio-clip-types) for the types

### v0.7.6 - 2026-11-24

+ **New pre-call network check `networkCheck`**: call it before joining, without joining a channel. It checks 5 items in order: network permission, network connection, MTU, DNS resolution, and server connectivity (SDK API, signaling, media). `onItem` reports progress item by item, and the call finally returns a summary, with each item carrying a description you can show to users directly. Call `cancelNetworkCheck()` to cancel. On the Web, the network permission, MTU, and DNS resolution items are reported as "not supported" due to browser limitations. The check requires the server to provide the network check API; with an older server version, the server connectivity item fails. See [SRTC · networkCheck](/en/rtc/web/api-reference/SRTC#networkcheck) for usage and [Pre-call network check types](/en/rtc/web/types#pre-call-network-check-types) for the types

### v0.7.5 - 2026-11-23

+ **Runtime environment and peripherals visible in the log center**: after joining, the SDK reports the browser, operating system, and peripheral list (including device names), and also records microphone / camera switches and changes to the playback device for remote audio, making on-site issues such as echo or no sound easier to troubleshoot
+ **Fixed missing video or audio after resubscribing**: when an unsubscribe request didn't reach the server because of network issues, subscribing to the same stream again no longer ends up "subscribed but with no data"

### v0.7.4 - 2026-11-19

+ **`getVolume()` now works**: on local audio tracks (microphone and others), `getVolume()` used to always return 0. It now returns the input volume from 0 to 100 (0 below about -45 dBFS, 100 above about -10 dBFS), ready to drive a microphone level meter. See [Media tracks](/en/rtc/web/api-reference/media-tracks)
+ **Media reconnection failures are no longer silent**: when automatic reconnection of the SFU media connection finally gives up (the server returns an unrecoverable error, or repeated retries fail), the SDK emits `DISCONNECTED` with the reason, instead of leaving the user in the channel with no audio or video. Make sure your app handles this event
+ **Members and tracks are restored after a lost session**: after the signaling connection drops, if the server has lost the session (for example after a long disconnection), the SDK fetches the channel details again on reconnect, emits the member join/leave and track add/remove events missed while disconnected, and then emits `RECONNECTED`. Short disconnections are still covered by the server re-sending messages
+ **Joining no longer hangs on a network hiccup**: if the signaling connection fails on its first attempt during join and then succeeds on retry, `join` now returns instead of hanging
+ **Users who rejoin are no longer removed by mistake**: a late leave message from a user's old session no longer removes them after they rejoin
+ **No more spurious `USER_TRACK_UPDATE`**: track update events are no longer emitted on every stream update when the remote tracks haven't changed

### v0.7.3 - 2026-11-16

+ **Browser noise suppression is turned off automatically with noise suppression plugins**: when you use the [RNNoise](/en/rtc/web/advanced/rnnoise) or [DeepFilterNet](/en/rtc/web/advanced/deepfilternet) plugin, the SDK turns off the browser's own noise suppression and restores it on detach, so the two don't stack and muffle voices. Upgrade the plugins as well (RNNoise 0.1.1, DeepFilterNet 0.1.2)
+ **New audio processor interface `AudioTrackProcessor`**: a custom audio processor can use `audioProcessing` to declare what it needs from the browser's noise suppression, echo cancellation, and auto gain control. See [Audio/video processors](/en/rtc/web/advanced/audio-processor)
+ **Microphone and camera actually stop when a processor is attached**: previously, with a processor attached, `stopCapture` or switching devices didn't stop the original microphone or camera, so the browser's recording or camera indicator stayed on
+ **Calling `setProcessor` again no longer causes silence or a black screen**: calling `setProcessor` while a processor was already attached could hand the new processor a dead track, resulting in silence or a black screen

### v0.7.2 - 2026-11-09

+ **Microphone no longer fails along with an unusable camera**: when listing devices (`getDevices`), if a camera is present but cannot be started (held by another app, broken VDI camera redirection, etc. — the browser reports `NotReadableError`), the microphone used to fail with it and no device list was returned. The SDK now retries with the microphone only, so the user can still unmute

### v0.7.1 - 2026-11-04

+ **Works with webpack 4 and other older toolchains**: the build output is now down-leveled to ES2019 (class fields, optional chaining, BigInt literals, and similar syntax are transpiled). This fixes the `Module parse failed` error when the SDK is imported with webpack 4, or with older babel setups that do not transpile `node_modules`. APIs and runtime behavior are unchanged; the bundle is about 7% larger

### v0.7.0 - 2026-09-30

<Warning>
**This release contains breaking changes**: error codes are renumbered across the board, the SDK's error messages are now in English, and a `language` parameter is added. Any code that branches on the numeric `code` (especially `106000`), on Chinese error text, or on the browser's raw exceptions needs to be updated according to the table below. For the full tables, see [Error codes](/en/rtc/web/error-codes) and [Error code format and unified table](/en/rtc/error-codes).
</Warning>

#### Breaking changes
+ **Error codes renumbered**: the SDK's own errors get low 3-digit codes from the cross-platform unified table instead of mostly falling into `106000`. Check `code` / `baseCode`, not the message text
+ **Error messages in English**: the `message` / `msg` of the SDK's own errors are now all in English and meant for developers and logs; map codes to your own end-user messages (the error code page has a "Suggested user message" column)
+ `SdkError` now extends `Error` (it has `message`, `name`, and `stack`, `e instanceof Error` holds, and `msg` is kept for compatibility); `baseCode` (the low 3-digit code) is added; the package exports `SdkError` and `ErrorCode`
+ HTTP non-200 responses / failed network requests now always throw `SdkError(106006)`, with the HTTP status in `message` (previously an `Error` with no code, such as `"500:..."`)
+ Capture failures (`startCapture`, requesting device permissions) now throw a coded `SdkError` instead of the browser's raw exception: `name` and `message` keep the browser's original values (such as `NotAllowedError`) and the original exception is in `cause`, so existing code that checks `e.name` keeps working
+ When an API returns HTTP 200 but the body has no `code` field, it used to be treated as a server business error (heartbeat left the channel immediately); it's now a response parse failure `106011` and is retried. A body that isn't JSON is also `106011`
+ Calling `publishLocalTrack` or `subscribeRemote*` on a channel that has been left (or is being left) throws `106001` (`Channel has been left`); `unpublishLocalTrack` / `unsubscribeRemoteTrack` still succeed silently after leaving the channel

#### New
+ **`language`** init parameter (for example `zh-CN` or `en`; if omitted, follows `navigator.language`, falling back to `zh`): the SDK sends `Accept-Language` with its server requests, and **the messages of server business errors (`1000`–`99999`) come back in Chinese or English accordingly**. The SDK's own errors are always in English and aren't affected. See [Types · SdkInitParams](/en/rtc/web/types#sdkinitparams)
+ The prompt shown when autoplay is blocked has built-in Chinese / English text (chosen by `language`), which you can override with the `autoPlayDialogText` init parameter; `disableAutoPlayDialog` behaves as before

#### Fixes
+ The autoplay prompt no longer includes the track desc and is built as plain text, fixing HTML injection through a remote desc

#### Changes
+ The track `toString()` prefix now uses class-name style (such as `LocalCameraTrack[...]`), so track names in the logs are now in English; `QualityEvaluation.reasons` of connection quality evaluation is now in English (for diagnostics, not a contract)
+ The npm page description is now bilingual (Chinese and English), and the license is now proprietary (UNLICENSED)

#### Old code → new code mapping

| Scenario | 0.6.x and earlier | 0.7.0 |
| --- | --- | --- |
| Not in the channel / token expired / track doesn't exist | `106001` / `106002` / `106003` | Unchanged (message now in English) |
| Other SDK errors (invalid argument, invalid state, publish description conflict, publishing before capture, publish / subscribe limit exceeded, browser not supported, and so on) | `106000` | Scenario-specific codes; see [Error codes](/en/rtc/web/error-codes) |
| HTTP non-200 / failed network request | `Error` with no code | `106006` |
| Response isn't JSON / missing the `code` field | Raw parse exception / treated as a server error | `106011` |
| Camera / microphone permission denied | Browser `NotAllowedError` | `106231` / `106251` (`name` is still `NotAllowedError`) |
| Screen sharing canceled or not allowed | Browser `NotAllowedError` | `106039` |
| Device doesn't exist or was unplugged | Browser `NotFoundError` / `OverconstrainedError` | `106021` |
| Device in use / hardware error | Browser `NotReadableError` and similar | `106018` |
| Publishing while the media streaming engine is reconnecting | `106014` | `106014` (unchanged) |
| Publishing / subscribing while the media streaming engine isn't connected / is disconnected (not reconnecting) | `106014` | `106300` / `106301` |
| The publish / subscribe media connection entered failed / closed | The strings "发布失败" / "订阅失败" | `106015` |
| CDN engine publish / subscribe negotiation timed out | The strings "发布超时" / "订阅超时" | `106302` / `106303` |
| Media connection timed out when joining the channel | `Error` with no code | `106007` |
| Server business errors (`1000`–`99999`) | Passed through | Passed through; messages come back in Chinese or English according to `language` |

### v0.6.3 - 2026-09-23

+ fix: local audio mixing now outputs directly through AudioContext, fixing dull received audio on Web
+ fix: the hidden audio elements used internally by mixing to activate remote tracks are now muted and kept referenced, preventing mixing from occasionally going silent after they were garbage-collected
