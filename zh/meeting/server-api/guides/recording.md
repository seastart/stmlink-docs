本页讲云录制与合流的整体玩法。单个接口的参数与返回结构见[会议录制与直播](/zh/meeting/server-api/mcu)。

<Tip>要把会议画面拉出去播放（HTTP-FLV / RTSP）或推到直播平台（RTMP / RTMPS），见[媒体输出接入指南](/zh/meeting/server-api/guides/media-output)：会议里有合流任务时用 `video=mcu` 取合成画面，也可以取任意一个人的画面。</Tip>

## 一个任务，三种能力

`task_type` 是**按位组合**的，三个独立能力各占一位，想同时要哪几个就相加：

| 值 | 能力 | 产物 | 怎么取 |
| --- | --- | --- | --- |
| 1 | 录像 | 录像文件（可能多段） | [单个录像文件的点播地址](/zh/meeting/server-api/mcu#单个录像文件的点播地址) |
| 2 | 合流 | 合成画面与会议混音 | 用[媒体输出](/zh/meeting/server-api/guides/media-output)拉流或推流（`video=mcu`） |
| 4 | 录音 | 纯音频文件 | 同录像 |

所以 `3` = 录像+合流，`7` = 三种全开。

<Warning>不要把 `3` 理解成「混合模式」这一种独立类型。早前的文档把值域写成「1录像 2合流 3混合」，那是错的 —— 既漏了录音，也误导了组合语义。</Warning>

<Note>原来的类型 `8`（直播流）已删除，传 `8` 或含 `8` 的组合返回参数错误 `10070`（请求参数不合法）。直播请用 `2`（合流）+ [媒体输出](/zh/meeting/server-api/guides/media-output)拉流或推流。升级时历史任务的 `task_type` 会把 `8` 换成 `2`（如 `9` → `3`）。</Note>

## 有些任务会自动启动

这是 SMeeting 与底层 SRTC 最不一样的地方：**不是所有录制都要你手动调 start**。
第一个人进会时，服务端会按会议自身的配置决定要不要起任务：

| 会议情况 | 自动启动的 `task_type` |
| --- | --- |
| 普通会议，`auto_record` 关 | 不启动 |
| 普通会议，`auto_record` 开 | `1` 录像 |
| 合成模式的**预约**会议，`auto_record` 关 | `2` 合流 |
| 合成模式的**预约**会议，`auto_record` 开 | `3` 录像+合流 |

若部署时开了直播能力，普通会议开了 `auto_record` 时会顺带合流，实际起的是 `3`（录像+合流），
以便直接用合成画面拉流或推流。这个开关由部署决定，不由接口控制，不确定的话问一下我们。

自动启动用的布局是会议自己的 `layout_data`（创建 / 修改会议时传），没配就用服务端默认布局（默认为 `auto`）。

所以：**创建会议时把 `auto_record` 设成 `true`，就不用在业务里管录制的启停了。**
手动调 [start](/zh/meeting/server-api/mcu#开始--更新录制任务) 适用于「会议中途才决定要录」这类场景。

## 同一场会议重复调 start 是更新，不是新建

同一个会议对同一类型只有一个进行中的任务。用不同参数再调一次 `start`，改的是现有任务
（例如换布局），不会多出一个任务，也不会产生第二个录像文件。

## 录像和直播的关键区别

| | 录像 | 直播（媒体输出） |
| --- | --- | --- |
| 何时能取到地址 | 收到 `mcu_record_done` 回调后 | 合流任务**进行中**就能拉流或推流 |
| 用途 | 事后回放、归档 | 把画面分发给不参与互动的观众 |
| 地址有效期 | 有，每次播放前重新获取 | 拉流地址默认 24 小时，每次播放前重新获取 |

直播的拉流与推流见[媒体输出接入指南](/zh/meeting/server-api/guides/media-output)。`mcu/start` 原来的 `layout_data.push_url` 推流参数已删除，改用 `stream/push/start`。

<Note>取回放地址请等 [`mcu_record_done` 回调](/zh/meeting/server-api/guides/callbacks)，不要在任务一结束就取 —— 那时转码往往还没完成。</Note>

## 画面怎么排

`layout_data.layout` 决定画面布局，分两类：

+ **`auto` 自动布局**：只给有视频画面的人分格子，按人数自动选宫格，人数变了跟着切换。**绝大多数场景够用**。自动布局下 `div_list` 不生效
+ **固定布局**：画面结构不随人数变化，可以配合 `div_list` 把指定的人钉到指定格子（见下一节）

`layout` 不传时使用服务端默认布局（默认为 `auto`，可由部署方调整）。

| 取值 | 画面 | 格子数 | 大画面的格子序号 |
| --- | --- | --- | --- |
| `auto` | 自动：1 人全屏；2–6 人对应 `grids_2`–`grids_6`；7–9 人 `grids_9`；10–12 人 `grids_12`；13–16 人 `grids_16`；17–20 人 `grids_20`；更多人 `grids_25`（最多显示 25 人）| 随人数 | — |
| `full` | 全屏单画面 | 1 | 0 |
| `grids_N` | 等分宫格，N 取 2、3、4、5、6、8、9、12、16、20、25（`grids_3` 是品字形）| N | 无，格子等大 |
| `right_4` | 右侧小窗：左边大画面 + 右边一列 4 个小窗 | 5 | 0 |
| `top_4` | 顶部小窗：顶部一行 4 个小窗 + 下方大画面 | 5 | 4 |
| `br_7` | 下 L 型：左上大画面 + 右边一列 3 个、底部一行 4 个小窗 | 8 | 0 |
| `tl_7` | 上 L 型：顶部一行 4 个、左边一列 3 个小窗 + 右下大画面 | 8 | 5 |
| `tb_8` | 左右布局：中间左右两个大画面 + 顶部、底部各一行 4 个小窗 | 10 | 4、5 |
| `ring_16` | 大回字型：5×5 宫格合并中间 9 格为一个大画面，外圈 16 个小窗 | 17 | 6 |
| `ring_12` | 小回字型：4×4 宫格合并中间 4 格为一个大画面，外圈 12 个小窗 | 13 | 5 |

<Warning>传了表里没有的值**不会报错**，会静默按 `auto` 处理。`grids_N` 的 N 不连续（没有 7、10、11），拼写前对一下表。</Warning>

**水印与成员名标签可以用默认值，布局不行。** `layout_data` 里没传 `watermark` / `tag` 时，
用[录制配置](/zh/meeting/server-api/mcu#获取录制配置)里的 `watermark_type` / `window_tag_type`；但布局不从录制配置取 —— 需要固定布局，
每次启动任务都要在 `layout_data.layout` 里传。

## 指定谁出现在哪个格子

`layout_data.div_list` 只对**固定布局**生效。每个元素钉一个格子：

+ `cells[0].idx`：格子序号，从 `0` 开始，顺序等同 HTML 表格里 `<td>` 的排列（从左到右、从上到下）；大画面的序号见上表。**必须小于该布局的格子数**
+ `uids[0]`：钉在这个格子的人（填 `user_id`）。这个人不在会议里时，格子留空等他
+ `cells[0].bind_share` 为 `true` 时，这个格子固定显示当前的共享画面（不区分是谁在共享，此时 `uids` 不看）；没人共享时格子留空
+ 一个元素里 `cells`、`uids` 都只取**第一个**，多填的会被忽略 —— 要钉多个格子就在 `div_list` 里放多个元素

没被钉住的格子怎么填，由 `polling_dur` 决定：

| `polling_dur` | 剩余格子 |
| --- | --- |
| `0`（默认） | **空着**，不会自动填人 |
| 大于 `0` | 由其余有视频画面的人按进会议先后依次填入；人比格子多时每隔 `polling_dur` 秒轮换一批（小于 5 按 5 秒算）|

所以固定布局想「指定几个人、其余人自动排」，**一定要设 `polling_dur`**，否则只有钉住的格子有画面。

典型用法：「主讲人固定在大画面、共享固定在一个小窗、其余人在剩下的小窗里轮播」：

```json
{
  "layout": "right_4",
  "polling_dur": 10,
  "div_list": [
    { "cells": [{ "idx": 0 }], "uids": ["主讲人的 user_id"] },
    { "cells": [{ "idx": 1, "bind_share": true }] }
  ]
}
```

## 无人时的行为

`layout_data.nobody_text` 决定会议里没人时怎么办：

+ **留空** → 暂停录制（推荐，避免录出大段黑屏）
+ **填了文本** → 继续录制并显示该文本

## 水印与成员名标签

+ `watermark.type`：`0` 默认、`1` 无、`2` 单排、`3` 多排。`watermark.text` 留空时用会议标题作为水印内容
+ 成员名标签的位置用字母组合表示：`L` 左、`R` 右、`T` 上、`B` 下，可组合（`LB` = 左下）。**留空表示不显示标签**
+ 字号、颜色、轮廓都留默认值即可，只在有明确视觉要求时才指定

## 完整时序

```text
1. 可选：配好应用的默认录制配置     POST /server/v1/mcu/save-record-config
2. 创建会议时设 auto_record         POST /server/v1/meet/create
   → 第一个人进会时任务自动启动，跳到第 5 步
   或：会议中途手动启动             POST /server/v1/mcu/start        → task_id
3. 有合流任务 → 可拉流 / 推流      POST /server/v1/stream/pull-url、stream/push/start
4. 结束                             POST /server/v1/mcu/stop
5. 收到 mcu_record_done 回调后取回放 POST /server/v1/mcu/vod-url   （按 record_id 取一段）
   要整场的全部段                    POST /server/v1/mcu/vods-url
```

## 一次录制会产出多个文件

**录像不是"一次录制一个文件"。** 两种情况会切出多个文件：

+ 录制时长超过分片上限（默认 1 小时）：任务结束后转码时按时长滚动切段，片间时间连续
+ 录制中途底层因 30 秒无音视频流自动停止、随后被重新拉起：另起一段，**片间存在时间空洞**

因此对接时注意三点：

1. **取地址用 `record_id` 而不是 `task_id`。** `mcu_record_done` 回调按文件推送，一次录制推多条，
   每条带自己的 `record_id`；`task_id` 是整个任务的，拿它只能定位到任务。
2. **`vods-url` 一次给你整场的全部段**，按分片序号排好，每段带 `record_id` / `seq` / `began_at` /
   `duration` / `offset_ms`。做连播时按 `seq` 顺序播，用 `offset_ms` 拼进度轴。
3. **`reason=2` 的那一段与上一段之间有时间空洞**（录制曾中断），连播会跳变，UI 上值得给个提示。

`vods-url` 的 `url` / `size` / `mcu_at` / `mcu_dur` 四个字段语义不变（`mcu_at` 是本段开始时间、
`mcu_dur` 是本段时长），此前已按这套字段对接的不必改动。

<Note>
  录像文件是**任务结束之后**才开始转码上传的。所以停止录制到"能播"之间有一段等待，
  长录制会更久。判断"能播了"要靠 `mcu_record_done` 回调（最后一条的 `is_last` 为 `true`），
  不要以任务状态变成"已结束"为准。
</Note>

## 计费提示

录制、合流、录音（以及推流）都是持续产生费用的服务端能力。`auto_record` 开着就意味着每一场会议都在录 ——
上线前确认这是你要的。手动启动的任务，业务侧最好在会议结束流程里显式调 stop。
