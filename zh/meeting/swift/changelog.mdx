### [1.5.0] - 2026.10.10
<Warning>
**`AgentStatus`（可邀请设备的在线状态）取值已改为与服务端一致**：旧版定义是 `idle = 1`（空闲）/ `busy = 2`（忙碌）/ `offline = 3`（离线），与服务端不符 —— 服务端会下发 `status = 0`，旧版遇到它整页 SIP / H323 / RTSP / GB28181 设备列表解码失败。新定义为 `unknown = 0`（未知）/ `online = 1`（在线）/ `offline = 2`（离线），服务端出现其它取值时解成 `.unknown`。旧名 `idle` / `busy` 保留为废弃别名（分别等于 `.online` / `.offline`），源码照常编译；**但按 `rawValue` 与数字比较（如 `== 3` 判离线）的代码升级后行为会变，需要自查**。版本号只升 minor，按 `from: "1.4.x"` 接入的工程会**自动**解析到本版。
</Warning>

#### 新增
+ **IM 事件真正派发**：`enableIm` 之后，被叫（`meeting(_:imCallCalling:)`）、会议提醒（`imMeetingRemind`）、等候室放行（`imAdminMoveOutWaitingRoom`）、小组求助（`imUserHelpSubMeeting`）以及 IM 重连中 / 已重连 / 被动断开这几个回调现在都会触发（旧版这些回调没有派发点，永远收不到）。新增 `meeting(_:imDidConnect:)`（`ImConnectEventData`）与 `meeting(_:imDidReceiveMessage:)`（`ImMessageEventData`，任何 action 的原始消息透传）。`ImMeetingRemindContent` 新增 `creatorId`；`ImDisconnectEventData` 新增 `disconnectReason`、`errorCode`、`errorMessage`。主动 `disableIm` 不再上抛断开回调。
+ **签到导出**：`signInExportDetail(epoch:destination:)`，下载签到明细落盘并返回本地文件地址。
+ **小组里拉主会场在线成员**：新增重载 `adminListOnlineMember(meetingId:page:perPage:)`，原方法不变。
+ **转移主持人带出原主持人**：新增 `meeting(_:roomHostDidMove:)`（`RoomHostMoveEventData`，含原主持人 `sourceUid`），原主持人本地降为普通成员并补发 `userRoleDidChange`。
+ **系统消息与普通聊天分离**：`RoomChatMsgEventData` 新增 `action` 与 `isSystem`，主持人发出的系统消息可以与普通聊天区分。
+ `MeetingInfo` 新增 `entryMutePolicy`（入会静音策略）与 `content`，均为可选，缺失或取值不认识时为 `nil`。
+ `AgentInfo` 新增 `connParams`（连接参数）与 `connSubjects`（GB28181 通道表）及公开构造器。国标设备要按「设备编号:通道编号」邀请，通道展开由调用方完成。

#### 修复
+ **`detailRoom`（会议详情）必失败**：服务端的会议详情回包不带 `created_at`，旧版每次抛 `responseParseFailed`，会议详情、按房间号加入、从被叫 / 提醒 / 求助入会都走不通。现在缺失时按 0 解码。
+ **几处列表的宽松解码**：空小组的 `users` 为 `null`、等候室列表不带 `avatar`、在线成员的 `device_type` / `join_at` 为整数，此前都会让整张列表解码失败。

#### 变更
+ SRTC 依赖升至 **1.5.2**（iOS 音频会话两处修复，见音视频 SDK 的[更新日志](/zh/rtc/swift/changelog)）。
+ `ImEventType` 新增 `connected`、`message`，`RoomEventType` 新增 `roomHostMoved`。

<Note>
`SMeetingDelegate` 新增的回调都有默认实现，不实现不影响编译；对 `ImEventType` / `RoomEventType` 做 `switch` 的代码请带上 `@unknown default` 分支。平台下限不变（iOS 16 / macOS 14）。

做 iOS 全屏屏幕共享的接入方，扩展 target 那条 `srtc-swift-sdk` 依赖要一并改为 `exact: "1.5.2"`，与本版清单里 pin 的 SRTC 版本一致，否则依赖解析失败。
</Note>

### [1.4.1] - 2026.10.01
<Warning>
**`McuTaskStatus` 的原始值已改正**：旧版的定义与服务端下发的 `task_status` 错位（旧版 `exception = 2`、`normal = 3`，而服务端的 2 是「待结束」、3 才是「异常结束」、4 才是「正常结束」），导致服务端的「异常结束」被识别成 `.normal`、「待结束」被识别成 `.exception`，而真正的「正常结束」与「待开始」事件被直接丢弃、`meeting(_:roomMcuTask:)` 收不到。成员名不变、原始值已改正，按成员名（`.normal` / `.exception`）判断的代码升级后即得到正确语义；**直接拿 `rawValue` 与数字比较的代码需要自查**。
</Warning>

#### 修复
+ **`McuTaskStatus` 与服务端取值对齐**：`waitStart = 0`（待开始）、`running = 1`、`waitEnd = 2`（待结束）、`exception = 3`、`normal = 4`；`waitStart` / `waitEnd` 是指令已下发、底层任务尚未确认的临时过渡状态。
+ **`mcu_task` 事件遇到不认识的取值不再整条丢弃**：此前服务端下发本版本 SDK 不认识的 `task_type` / `task_status` 时，`meeting(_:roomMcuTask:)` 根本不会回调。现在照常回调，枚举落到新增的 `.unknown`，原始值见 `RoomMcuTaskEventData` 新增的 `taskTypeRaw` / `taskStatusRaw`。
+ **`mcuRecordDetail(meetingId:)` 适配服务端新的「任务 + 录制文件」两级返回**：服务端已把任务 ID 的键名改为 `task_id`，并把录像文件信息下沉到分片列表，旧版在新服务端上解码失败、直接抛错。现在新老服务端的返回都能解出来，缺失的字段取零值。

#### 新增
+ `McuTaskType` 新增 `audio = 4`（录音）、`live = 8`（直播流）与兜底的 `unknown = -1`；`McuTaskStatus` 新增 `waitStart`、`waitEnd` 与 `unknown`。`unknown` 只用于解码，不要拿来发请求。
+ `McuRecordDetail` 新增 `taskType`、`beganAt`、`endedAt`、`recordCount`、`totalDuration`、`totalSize`、`records`、`now`；新增录制文件类型 `McuRecordFile`（`recordId`、`seq`、`vodSize`、`duration`、`beganAt`、`endedAt`、`offsetMs`、`reason`、`addr` 等，`addr` 为有效期 2 小时的预签名播放地址）。

#### 变更
+ `McuRecordDetail` 的 `vodKey`、`vodSize`、`mcuAt`、`mcuDur` 标为废弃，类型改为可选（新服务端不再返回 `vodKey` / `vodSize`）：录像文件改看 `records`，`vodSize` → `totalSize`，`mcuAt` → `beganAt`，`mcuDur` → `totalDuration`。
+ SRTC 依赖升至 **1.5.1**（`AudioRoute.displayName` 按系统语言返回中 / 英文，见音视频 SDK 的[更新日志](/zh/rtc/swift/changelog)）。

<Note>
升级时需要留意两处编译层面的变化：用到 `McuRecordDetail.vodKey` 等四个字段的代码会出现废弃告警，且它们变成了可选类型，按非可选使用的地方要改（建议直接换成上面的新字段）；对 `McuTaskStatus` / `McuTaskType` 做 `switch` 的代码，请带上 `@unknown default` 分支。平台下限不变（iOS 16 / macOS 14）。

做 iOS 全屏屏幕共享的接入方，扩展 target 那条 `srtc-swift-sdk` 依赖要一并改为 `exact: "1.5.1"`，与本版清单里 pin 的 SRTC 版本一致，否则依赖解析失败。
</Note>

### [1.4.0] - 2026.09.30
<Warning>
**本版是破坏性变更**：错误码按跨端统一码表（第 2 版）调整，报错文案改为英文。凡是按 `SMeetingError.code` 的数值、或按 `message` / `localizedDescription` 的中文文字做判断的代码，升级后都需要调整；下表中「改抛了另一个 case」的场景，`switch` 分支也要改。版本号只升 minor，按 `from: "1.3.x"` 接入的工程会**自动**解析到本版，升级前请先看完下表。
</Warning>

#### 新增
+ **`SMeetingEngine.language`**（`String?`，如 `"en"`、`"zh-CN"`；`nil` = 跟随系统语言）与只读的 **`currentLanguage`**。它与 `meeting.srtc.language` 是**同一个进程级设置**：会议层和 RTC 层请求后端都带 `Accept-Language`，**后端业务错误（码 ≥ 1000）的文案随之中 / 英**；SDK 自身的报错一律英文，不受它影响。建议在 `login` 之前设置。
+ **`SMeetingError.baseCode`**（低 3 位语义码，跨端统一）与 **`httpStatus`**（HTTP 非 200 时的状态码，仅 `httpError` 有值）。
+ **`SMeetingError` 实现 `CustomNSError`**：桥接成 `NSError` 后 `domain = "cn.seastart.smeeting"`、`code` 为完整码（如 `203003`）。
+ 新增错误 case：`httpError(status:message:)`（007）、`userNotFound`（010）、`invalidState`（011）、`invalidArgument`（012）、`remoteTrackUnavailable(uid:desc:)`（209）、`requestTimeout`（353）、`requestCancelled`（354）、`responseParseFailed`（356）。

#### 变更
+ **报错文案全部改为英文**（如 `notLoggedIn` 由「您尚未登录meeting sdk」改为 `Not logged in to the meeting SDK`）。`message` 是给开发者和日志看的，**给终端用户的提示请按 `code` / `baseCode` 自行映射**，不要直接展示 `message`。
+ **HTTP 状态码不再拼进错误码**：此前 HTTP 500 会报成 `203500`、响应解析失败会算出 `202999` 这类码，现在 HTTP 非 200 报 `httpError`（`203007`，状态在 `httpStatus`），响应解析失败报 `responseParseFailed`（`203356`）。
+ 采集 / 权限错误原样透传 RTC 层的 `SRTCError`（如 `103231` 无摄像头权限、`103251` 无麦克风权限、`103039` 屏幕共享被拒），`catch` 时两类都要处理。
+ SRTC 依赖升至 **1.5.0**（同样是错误码重排 + 英文化，见音视频 SDK 的[更新日志](/zh/rtc/swift/changelog)）。

#### 旧码 → 新码对照
iOS 前缀为 `203`、macOS 为 `205`，下表以 iOS 为例（macOS 把前缀换成 `205`）。

| 场景 | 1.3.10 及以前 | 1.4.0 |
| --- | --- | --- |
| HTTP 非 200 | `203<HTTP 状态>`（如 `203500`），`apiError` | `203007` `httpError`（`httpStatus` 为 HTTP 状态） |
| 响应不是 JSON / 缺 `code` 字段 | `202999` `apiError` | `203356` `responseParseFailed` |
| 响应 `data` 结构与预期不符 | 原样抛出 `DecodingError` | `203356` `responseParseFailed` |
| 网络请求失败（URLSession） | 原样抛出系统错误 | `203007` `networkError` |
| 请求超时 | 原样抛出系统错误 | `203353` `requestTimeout` |
| 请求被取消 | 原样抛出系统错误 | `203354` `requestCancelled` |
| 房间内没有该用户 | `203009` `internalError` | `203010` `userNotFound` |
| 找不到远端用户的轨道 / MCU 合成视频轨道 | `203009` `internalError` | `203209` `remoteTrackUnavailable` |
| 尚未开启摄像头 | `203008` `deviceError` | `203011` `invalidState` |
| 全屏采集未 `prepareBroadcastShare` / 已开启共享 / 共享中开启视图录制 | `203009` `internalError` | `203011` `invalidState` |
| RTC 层错误（采集、权限、推拉流） | `SRTCError` 旧码 | `SRTCError` 新码（见 SRTC 1.5.0 对照表） |

未变化的码：`notLoggedIn` 001、`tokenExpired` 002、`notInMeeting` 003、`unauthorized` 004、`tokenInvalid` 005、`alreadyInMeeting` 006、`deviceError` 008、`internalError` 009（仅文案改英文）。后端业务码（≥ 1000）仍原样透传，文案现在随 `language` 返回中文或英文。

<Note>
已有的 `SMeetingError` case 一个没删、签名没改，编译层面 1.3.10 的接入代码可直接升级；需要检查的是**按数值 / 中文文案判断错误、以及 `switch` 里依赖上表旧 case 的分支**。平台下限不变（iOS 16 / macOS 14）。

做 iOS 全屏共享的工程，扩展 target 那条额外的 `srtc-swift-sdk` 依赖需同步改为 `exact: "1.5.0"`，与本包清单里 pin 的版本保持一致，否则依赖解析会直接失败。
</Note>

### [1.3.9] - 2026.09.23
#### 修复
+ **主持人强停共享后，共享状态会被重新上抛**：`admin_stop_room_share` 此前只停了本端发布，没有同步清掉房间的共享状态（`share_state` / `share_uid`）。残留的状态会被随后到达的轨道或属性刷新重新判定成「有人正在共享」，表现为**共享刚被强停就又冒出来、房内出现停不掉的共享**。现在强停时一并收敛房间状态。
+ **屏幕共享开始事件补上第四条汇合路径**：1.3.8 的三路汇合仍漏了「用户快照刷新（`freshUserInfo`）先于其它三路到达」这一时序。此时快照会把 `shareState` 静默改成 `screen`，各路径共用的防重条件反过来把后到的那一路也拦掉，结果是**事件一次都不发，房内其他人收不到共享、画面不显示**。现在快照刷新在 `shareState` 跃变时也会上抛事件，四路中谁最后到齐由谁触发。该跃变判定只对远端生效，本端共享仍由发布与停止流程显式上抛。
+ **共享者直接离会后，会议永久停在「某人正在共享」**：共享方进程被杀或断网时不会有 `user_stop_room_share`，此前没有任何路径收敛，画面一直挂着。现在在成员离房（`userDidLeave`）时收敛房间共享状态并上抛停止事件——「人已离房」不是暂态，比轨道消失可靠。

#### 变更
+ SRTC 依赖保持 **1.4.6** 不变，本版只有会议层改动，没有公开 API 变更。

<Note>
本版为纯修复，没有破坏性变更，1.3.8 的接入代码可直接升级。做 iOS 全屏共享的工程，扩展 target 那条额外的 `srtc-swift-sdk` 依赖仍为 `exact: "1.4.6"`，本次无需改动。

仍未覆盖「人还在会里、只有 Broadcast Extension 单独挂掉」这一种情况：此时既不会有 `user_stop_room_share`，也不会有成员离房事件。该场景需在共享方本端补齐，不要拿 `screen` 轨道消失当停止判据——轨道消失也可能只是网络抖动，会误撤画面。
</Note>

### [1.3.8] - 2026.09.23
#### 新增
+ **`updateLocalCameraView(_:)`**：在不中断采集的前提下，把本地摄像头预览的渲染器搬到另一个视图上。UIKit 宿主在宫格重建、首屏与视频墙切换这类布局变化里会销毁并重建承载预览的视图，此前只能关掉摄像头再开一次，现在直接搬迁即可。

#### 修复
+ **摄像头已开启时重复调用 `requestOpenCamera(view:)`，新传入的预览视图被忽略**：此前复用已有轨道的分支直接返回，新视图没有被接上，渲染器还挂在已从视图树上摘掉的旧视图，表现为**本端画面黑屏**（对端一切正常）。现在复用分支会把渲染器搬到新传入的视图上。
+ **已在会中的成员收不到屏幕共享开始事件**：屏幕共享的开始信号是异步汇合的——房间共享状态（`user_start_room_share` 广播、频道属性里的 `share_state` / `share_uid`）与 `screen` 轨道各走各的路径。此前两条路径各自判定，且没有覆盖属性刷新这一路：广播先到时轨道还没登记、轨道先到时房间状态还没刷新，两边都各自放弃，之后属性刷新到了也没有人补判，结果是**已经在会中的成员完全收不到 `ROOM_SHARE_START`，退出重进反而能看到**（重进走的是另一条已有共享的通知路径）。现改为三路汇合判定，谁最后到齐由谁触发，防重逻辑不变。

#### 变更
+ SRTC 依赖升级到 **1.4.6**（含摄像头方向与横屏屏幕共享画面倒 180° 两项修复，详见音视频 SDK 的[更新日志](/zh/rtc/swift/changelog)）。

<Warning>
做 iOS 全屏共享的工程，扩展 target 那条额外的 `srtc-swift-sdk` 依赖要**同步改为 `exact: "1.4.6"`**，与本包 pin 的版本保持一致，否则依赖解析冲突。横屏共享画面倒 180° 的修复落在 `SRTCBroadcastKit`（本次 **1.0.11**）里，扩展侧不升就不会生效。
</Warning>

<Note>
本版为纯新增 API + 修复，没有破坏性变更，1.3.7 的接入代码可直接升级。
</Note>

### [1.3.7] - 2026.09.18
#### 新增
+ **会议标题变化事件**：新增 `SMeetingDelegate` 的 `meeting(_:roomTitleDidChange:)` 回调、`RoomTitleChangeEventData`（`title` / `previousTitle`）与 `RoomEventType.roomTitleChanged`。主持人改主会议标题、以及小组会议改名（`adminUpdateSubMeetingTitle`）都会触发，对应老 `MeetingKit` 的 `onRoomMeetingTitleChanged:`。
+ **远端视频收流超时 / 恢复**：新增 `meeting(_:didChangeReceiveStreamStatus:)` 回调与 `RoomEventType.receiveStreamStatusChanged`，按轨道判定某一格画面是否停止出帧，用来开关「加载中」指示。载荷直接复用音视频 SDK 的 `ReceiveStreamStatus`，未再包一层会议专属结构。对应老 `MeetingKit` 的 `onReceiveStreamStatusChange:streamType:status:`。
+ **音频单元启停**：新增 `SMeetingEngine.setAudioModuleEnabled(_:)` 与 `isAudioModuleEnabled`（iOS），是音视频 SDK `AudioRouteSession` 同名接口的薄封装，供录像直播课这类纯本地播放场景使用。

#### 变更
+ SRTC 依赖升级到 **1.4.5**。

<Warning>
`setAudioModuleEnabled(false)` 期间**通话音频收不到也发不出**，本地播放结束后必须调回 `true`。重新入会会自动复位为 `true`，手动停用的状态不会跨会议泄漏。

做 iOS 全屏共享的工程，扩展 target 那条额外的 `srtc-swift-sdk` 依赖要**同步改为 `exact: "1.4.5"`**，与本包 pin 的版本保持一致，否则依赖解析冲突。
</Warning>

<Note>
`roomTitleDidChange` 的载荷**没有 `opUid`**：会议改名没有独立的广播指令，事件是频道属性更新后比对标题得出的，属性里只有结果没有操作者。后端补上对应广播指令后会再带上。

三个协议方法均带默认空实现，无破坏性变更，1.3.6 的接入代码可直接升级。

不要用 `connectionQualityDidChange` 代替收流状态事件：前者是整条链路的质量档位，不是某一路画面的卡顿，详见音视频 SDK 的[更新日志](/zh/rtc/swift/changelog)。
