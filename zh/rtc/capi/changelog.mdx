### [0.1.0] - 2026.09.30
本版统一了各端 SDK 的错误码，属于**破坏性变更**，版本号由 0.0.11 直接升到 0.1.0。

#### 破坏性变更
+ **错误码全面重排**：`rtc_get_last_error` 返回的 SDK 错误码改为「`180` + 3 位跨端统一码」，同一类错误在所有 SRTC SDK 上后三位相同，码表见 [错误码规则](/zh/rtc/error-codes) 与 [C SDK · 错误码](/zh/rtc/capi/error-codes)。以前落在 `180000`（一般错误）或 `-1`（无错误码）的失败，现在都有了具体的码。**代码里按错误码做判断的，请按下表修改**：

| 场景 | 旧码 | 新码 |
| --- | --- | --- |
| 无权发布合成流（非 `__mcu__` 身份） | `180004` | `180040` |
| Token 不合法（解析失败、缺字段） | `-1` | `180004` |
| 网络请求失败、HTTP 非 200 | `-1` | `180006` |
| `rtc_join_channel_sync` 入会超时 | `-1` | `180007` |
| 服务端响应无法解析 / 缺 `code` 字段 | `-1`（缺 `code` 时当作成功） | `180011` |
| 信令连接失败 / 信令订阅失败 | `180000` | `180009` / `180010` |
| 参数非法（`desc` 为空、未设宽高帧率、轨道类型不符等） | `180000` | `180031` |
| 频道正在重连 / 流媒体引擎未连接 | `180000` | `180014`（稍后重试即可） |
| 已离开频道后调用会中接口 | `180000` | `180001` |
| 流媒体引擎未初始化、轨道未就绪等调用顺序问题 | `180000` | `180024` |
| 超过发布上限 / 超过订阅上限 | `180000` | `180020` / `180034` |
| 频道内没有该用户 | `180000` | `180204` |
| 该用户没有指定 id / desc 的轨道 | `180000` | `180003` |
| 当前引擎不支持该能力（如切层） | `180000` | `180032` |
| 不支持的编解码器 | `-1` | `180019` |
| 创建轨道失败等 SDK 内部错误 | `-1` | `180025` |
| 发布 / 订阅被服务端拒绝（如 `1033` 并发已达上限、`1035` 节点满载） | `180300` / `180301` | 服务端原码（`1033` / `1035` 等）原样返回 |

+ **错误原因改为英文**：`rtc_get_last_error` 写入 `msg_buf` 的 SDK 错误原因改为英文（如 `Not in channel`）。请按错误码判断，不要按文案判断
+ 接口返回 `RTC_INVALID_PARAM` / `RTC_NOT_CONNECTED` 时，现在也会记录错误（`180031` / `180001`），`rtc_get_last_error` 不再取到上一次失败残留的错误

#### 新增
+ `rtc_set_language(const char* lang)`：设置语言（如 `"en"`、`"zh-CN"`），进程级生效，随时可调。它决定服务端业务错误（错误码 ≥1000）原因文案的语言；SDK 自身的错误原因始终是英文。不调用或传 `NULL` / 空串时跟随系统语言（环境变量 `LC_ALL` → `LC_MESSAGES` → `LANG`），系统语言为 `C` / `POSIX` 或都未设置时，服务端按中文返回，与旧版一致

#### 修复
+ **断网时心跳 / 重连直接退出频道**：网络请求失败被误当作服务端拒绝，导致短暂断网时不再重试就退出了频道。现在网络错误会继续重试，只有服务端明确拒绝才退出

<Note>
结构体布局与 0.0.11 一致，已有接口的函数签名不变。只替换库文件即可运行；要调用 `rtc_set_language` 需要用新的 `librtc.h` 重新编译。**按错误码写了判断逻辑的，务必按上表修改后再升级。**
</Note>

### [0.0.11] - 2026.09.26
#### 修复
+ **`rtc_destroy` 返回后回调仍可能在执行**：此前 `rtc_destroy` 只清空回调，不等已经在执行的回调返回，调用方在它之后释放 `context` 可能导致崩溃。现在 `rtc_destroy` 会等所有在途回调返回后才返回，返回后可安全释放 `context`
+ **销毁本地轨道后仍会触发关键帧回调**：`rtc_destroy_local_track` 现在会摘掉关键帧回调并等在途回调返回
+ **在断线回调里调用 `rtc_destroy` 会卡死**：现已支持在本实例的任意回调里销毁实例
+ 异步入会（`rtc_join_channel`）尚未完成就销毁实例时，频道不再一直挂着不离开

<Note>
接口与结构体布局与 0.0.10 完全一致，可直接替换库文件。此前为规避上述问题而在销毁后固定等待一段时间（sleep）的代码，升级后可以删掉。
</Note>

### [0.0.10] - 2026.09.26
#### 变更
+ 库文件去掉调试符号，Linux 版 `librtc.so` 体积约减小 27%（17.6MB → 12.8MB）。接口与行为无变化，崩溃时的堆栈仍会打印函数名与行号

<Note>
与 0.0.9 接口完全一致，已按 0.0.9 头文件编译的程序可以直接替换库文件。
</Note>

### [0.0.9] - 2026.09.26
#### 新增
+ `rtc_get_last_error`：接口返回 `RTC_ERROR` / `RTC_TIMEOUT` 后取具体错误码与原因，不必再翻日志
+ `rtc_set_disconnected_callback`：彻底断开时回调断线原因（被踢 / 顶号 / 心跳超时 / 频道销毁），宏 `RTC_DISCONNECT_*`
+ `rtc_get_local_user_info`：获取本端 uid / sid
+ `rtc_get_channel_info` / `rtc_free_channel_info` 与结构体 `rtc_channel_info_t`
+ 新增 macOS Apple Silicon 平台（`librtc.dylib`）

#### 修复
+ **加入频道快约 3 秒**：此前每次入会都要空等约 3 秒才开始建立信令连接，现在立即连接（实测入会耗时 3.4s → 0.4s）；断线重连的间隔不变
+ 修复实例句柄在特定时机被运行时判为非法指针、导致进程终止的问题
+ 频道流媒体引擎配置未知时回退到默认引擎，不再无法入会

#### 破坏性变更
+ **删除 `rtc_user_info_t.link_id` 字段**（此前恒为 0，无实际含义）

<Warning>
`rtc_user_info_t` 的内存布局随之变化。**从 0.0.8 及更早版本升级必须用新的 `librtc.h` 重新编译**，只替换库文件会读错 `stream_tracks` 等字段，甚至崩溃。代码里引用了 `link_id` 的地方直接删掉即可。
</Warning>

<Note>
回调的 `context` 必须是真实指针（或 `NULL`），不要把小整数强转成指针当 id 用，见 [实例与频道 · 回调注册](/zh/rtc/capi/api-reference/engine#回调注册)。
</Note>
