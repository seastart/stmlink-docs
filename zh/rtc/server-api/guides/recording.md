本页讲云录制与直播的整体玩法。单个接口的参数与返回结构见[云录制与直播](/zh/rtc/server-api/mcu)。

<Note>本页讲的是**整场**录制：整个频道混成一路。产出**不一定是一个文件** —— 长录制会按时长切段，见下文「一次录制会产出多个文件」。如果你要的是**按说话人分轨、按一次讲话切段**的录音，那是另一套接口，见[语音录制](/zh/rtc/server-api/talkrec)，两者的差异见下文对照表。</Note>

## 一个任务，四种能力

`task_type` 是**按位组合**的，四个独立能力各占一位，想同时要哪几个就相加：

| 值 | 能力 | 产物 | 怎么取 |
| --- | --- | --- | --- |
| 1 | 录像 | 录像文件（可能多段） | [获取单个录像文件的播放地址](/zh/rtc/server-api/mcu#获取单个录像文件的播放地址) |
| 2 | 合流 | 把多路流混成一路 | 旁路推流，给不支持多流的下游用 |
| 4 | 录音 | 纯音频文件 | 同录像 |
| 8 | 直播流 | HTTP-FLV 直播拉流地址，或推到你的直播平台 | [获取直播拉流地址](/zh/rtc/server-api/mcu#获取直播拉流地址)，见下文「直播：拉流与推流」 |

所以 `3` = 录像+合流，`9` = 录像+直播，`15` = 四种全开。

<Warning>不要把 `3` 理解成"混合模式"这一种独立类型。历史文档曾把值域写成「1录像 2合流 3混合」，那是错的 —— 既漏了录音与直播流，也误导了组合语义。</Warning>

## 一次录制会产出多个文件

**录像不是"一次录制一个文件"。** 两种情况会切出多个文件：

+ 录制时长超过分片上限（默认 1 小时）：任务结束后转码时按时长滚动切段，片间时间连续
+ 录制中途底层因 30 秒无音视频流自动停止、随后被重新拉起：另起一段，**片间存在时间空洞**

所以数据模型是**两级**的：一次录制 = 一个任务（`task_id`），任务下有 N 个录像文件（`record_id`）：

| 拿什么 | 用哪个接口 |
| --- | --- |
| 整场的全部可播地址（最常用） | [录像任务详情](/zh/rtc/server-api/mcu#录像任务详情)，`records` 数组里每段都带好了地址 |
| 分页翻某次录制的文件 | [录像文件列表](/zh/rtc/server-api/mcu#录像文件列表) |
| 单段地址 | [获取单个录像文件的播放地址](/zh/rtc/server-api/mcu#获取单个录像文件的播放地址)，传 `record_id` |
| 一次取回多段地址 | [批量获取录像文件播放地址](/zh/rtc/server-api/mcu#批量获取录像文件播放地址) |

每个文件带这几个字段，够你拼出完整回放：

+ `seq` 从 1 开始，按它排序就是播放顺序
+ `offset_ms` 是这一段相对整场录制开始的偏移（毫秒），做连播进度轴用它
+ `began_at` / `ended_at` 是墙钟时间，用来和你自己业务的时间线对齐
+ `reason=2` 表示**这一段与上一段之间有时间空洞**（录制曾中断后被重新拉起），连播会跳变

<Note>
  录像文件是**任务结束之后**才开始转码上传的。停止录制到"能播"之间有一段等待，长录制会更久。
  判断"能播了"要靠 `mcu_record` 回调（最后一条的 `is_last` 为 `true`），不要以任务状态
  变成"已结束"为准，见[回调事件接入指南](/zh/rtc/server-api/guides/callbacks)。
</Note>

### 「录音」和「语音录制」不是一回事

本页的 `task_type=4` 录音是 **MCU 合流录音**：整个频道混成一路音频，一次任务一个文件。

如果你要的是**按人分轨、按一次讲话切段**（对讲留痕、按人计时、逐句转写），用
[语音录制](/zh/rtc/server-api/talkrec)，那是另一套接口：

| | MCU 录音（`task_type=4`） | 语音录制（talkrec） |
| --- | --- | --- |
| 产物 | 整场混成一路（长录制会按时长切成多段） | 一次讲话一段，每段独立文件 |
| 分轨 | 不分，所有人混在一起 | 按说话人分轨，带 `uid` / `name` |
| 何时能取 | 任务停止且转码完成后 | 每段闭合就可取，边录边有 |
| 适合 | 归档整场音频 | 对讲、留痕、逐句处理 |

两者可以同时开，互不影响。

## 录像和直播的关键区别

| | 录像 | 直播 |
| --- | --- | --- |
| 何时能取到地址 | 任务**停止且转码完成**后 | 任务**进行中**就能取 |
| 用途 | 事后回放、归档 | 把画面分发给不参与互动的观众 |
| 地址有效期 | 有，每次播放前重新获取 | 有，默认 24 小时，每次播放前重新获取 |

这个差异决定了调用时序：直播是"开播即可分发"，录像是"结束后才有产物"。

## 直播：拉流与推流

`task_type` 带 `8` 的任务有两种用法，由开始任务时是否传 `layout_data.push_url` 决定：

| | 拉流模式（不传 `push_url`） | 推流模式（传 `push_url`） |
| --- | --- | --- |
| 观众怎么看 | 调[获取直播拉流地址](/zh/rtc/server-api/mcu#获取直播拉流地址)拿 HTTP-FLV 地址，网页用 flv.js 等播放器播放 | 你的直播平台 / CDN 负责分发 |
| 协议 | HTTP-FLV（H264 视频 + AAC 音频） | `rtmp://` 或 `rtmps://` |
| 声音 | `audio`：`mix` 全场混音（默认）/ `none` / `user` 指定用户 | `layout_data.push_audio`，取值同左 |
| 地址 | 自带签名，默认 24 小时有效，过期后新的拉流请求被拒、正在播的不断 | 你提供的推流地址（须带推流码） |

+ 视频都是按布局合成的画面；不再提供 RTMP、HLS 拉流地址（`live-url` 返回的 `rtmp`、`hls` 恒为空），需要它们时用推流模式推到你自己的平台
+ 推流模式下 `live-url` 返回错误码 `1048`；推流断线自动重连，持续失败时经 [`mcu_alarm` 回调](/zh/rtc/server-api/guides/callbacks)通知；没有可用的推流服务时开始任务返回 `1072`
+ 私有化部署需要部署媒体网关并放行相应端口，见[网络与端口要求](/zh/product/deploy/ports)

## 画面怎么排

`layout_data.layout` 决定画面布局，分两类：

+ **`auto` 自动布局**：只给有视频画面的人分格子，按人数自动选宫格，人数变了跟着切换。**绝大多数场景够用**。自动布局下 `div_list` 不生效
+ **固定布局**：画面结构不随人数变化，可以配合 `div_list` 把指定的人钉到指定格子（见下一节）

`layout` 不传时使用服务端默认布局（默认为 `auto`，可由部署方调整）。

| 取值 | 画面 | 格子数 | 大画面的格子序号 |
| --- | --- | --- | --- |
| `auto` | 自动：1 人全屏；2–6 人对应 `grids_2`–`grids_6`；7–9 人 `grids_9`；10–12 人 `grids_12`；13–16 人 `grids_16`；17–20 人 `grids_20`；更多人 `grids_25`（最多显示 25 人）| 随人数 | — |
| `full` | 全屏单画面 | 1 | 0 |
| `grids_N` | 等分宫格，N 取 2、3、4、5、6、8、9、12、16、20、25（`grids_3` 是品字形）| N | 无，格子等大 |
| `right_4` | 右侧小窗：左边大画面 + 右边一列 4 个小窗 | 5 | 0 |
| `top_4` | 顶部小窗：顶部一行 4 个小窗 + 下方大画面 | 5 | 4 |
| `br_7` | 下 L 型：左上大画面 + 右边一列 3 个、底部一行 4 个小窗 | 8 | 0 |
| `tl_7` | 上 L 型：顶部一行 4 个、左边一列 3 个小窗 + 右下大画面 | 8 | 5 |
| `tb_8` | 左右布局：中间左右两个大画面 + 顶部、底部各一行 4 个小窗 | 10 | 4、5 |
| `ring_16` | 大回字型：5×5 宫格合并中间 9 格为一个大画面，外圈 16 个小窗 | 17 | 6 |
| `ring_12` | 小回字型：4×4 宫格合并中间 4 格为一个大画面，外圈 12 个小窗 | 13 | 5 |

<Warning>传了表里没有的值**不会报错**，会静默按 `auto` 处理。`grids_N` 的 N 不连续（没有 7、10、11），拼写前对一下表。</Warning>

**水印与成员名标签可以用默认值，布局不行。** `layout_data` 里没传 `watermark` / `tag` 时，
用[默认录制配置](/zh/rtc/server-api/mcu#获取默认录制配置)里的 `watermark_type` / `window_tag_type`；但布局不从录制配置取 —— 需要固定布局，
每次启动任务都要在 `layout_data.layout` 里传。

## 指定谁出现在哪个格子

`layout_data.div_list` 只对**固定布局**生效。每个元素钉一个格子：

+ `cells[0].idx`：格子序号，从 `0` 开始，顺序等同 HTML 表格里 `<td>` 的排列（从左到右、从上到下）；大画面的序号见上表。**必须小于该布局的格子数**
+ `uids[0]`：钉在这个格子的人（填 `uid`）。这个人不在频道里时，格子留空等他
+ `cells[0].bind_share` 为 `true` 时，这个格子固定显示当前的共享画面（不区分是谁在共享，此时 `uids` 不看）；没人共享时格子留空
+ 一个元素里 `cells`、`uids` 都只取**第一个**，多填的会被忽略 —— 要钉多个格子就在 `div_list` 里放多个元素

没被钉住的格子怎么填，由 `polling_dur` 决定：

| `polling_dur` | 剩余格子 |
| --- | --- |
| `0`（默认） | **空着**，不会自动填人 |
| 大于 `0` | 由其余有视频画面的人按进频道先后依次填入；人比格子多时每隔 `polling_dur` 秒轮换一批（小于 5 按 5 秒算）|

所以固定布局想「指定几个人、其余人自动排」，**一定要设 `polling_dur`**，否则只有钉住的格子有画面。

典型用法：「主讲人固定在大画面、共享固定在一个小窗、其余人在剩下的小窗里轮播」：

```json
{
  "layout": "right_4",
  "polling_dur": 10,
  "div_list": [
    { "cells": [{ "idx": 0 }], "uids": ["主讲人的 uid"] },
    { "cells": [{ "idx": 1, "bind_share": true }] }
  ]
}
```

## 无人时的行为

`layout_data.nobody_text` 决定频道里没人时怎么办：

+ **留空** → 暂停录制（推荐，避免录出大段黑屏）
+ **填了文本** → 继续录制并显示该文本

## 水印与成员名标签

+ `watermark.type`：`0` 默认、`1` 无、`2` 单排、`3` 多排。`watermark.text` 留空时用任务的 `title` 作为水印内容
+ 成员名标签的位置用字母组合表示：`L` 左、`R` 右、`T` 上、`B` 下，可组合（`LB` = 左下）。**留空表示不显示标签**

## 完整时序

```text
1. 可选：配好应用的默认录制配置        POST /server/v1/mcu/save-record-config
2. 频道里有人后，启动任务              POST /server/v1/mcu/start        → task_id
   ├─ task_type 带 8 → 立即可取直播地址 POST /server/v1/mcu/live-url
   └─ 需要临时改布局 → 用同样参数重新调 start（同一频道同一类型是更新而非新建）
3. 结束                                POST /server/v1/mcu/stop
4. 转码完成后取回放                    POST /server/v1/mcu/vod-url
5. 归档整理                            POST /server/v1/mcu/update-record
```

频道销毁时进行中的任务会**自动停止**，不必先手动调 stop。

## 计费提示

录制、录音、直播都是持续产生费用的服务端能力。启动后若忘记停止，会一直跑到频道销毁为止——所以业务侧最好在会议结束流程里显式调 stop，不要只依赖频道销毁。
