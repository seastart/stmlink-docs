本页讲媒体输出的整体玩法：怎么选画面和声音、拉流和推流各自的限制、推流任务怎么管。
单个接口的参数与返回结构见[媒体输出](/zh/rtc/server-api/stream)。

## 一套来源，两种输出

媒体输出回答两个问题：**要什么**（画面、声音各取哪里）和**怎么给**（拉流还是推流）。两者独立：

| 输出 | 接口 | 协议 | 适合 |
| --- | --- | --- | --- |
| 拉流 | [申请拉流地址](/zh/rtc/server-api/stream#申请拉流地址) | HTTP-FLV、RTSP | 网页播放器、业务系统、NVR / 监控平台、转写或分析服务自己来拉 |
| 推流 | [开始推流](/zh/rtc/server-api/stream#开始推流) | RTMP、RTMPS | 推到视频号、抖音、自建 CDN 等直播平台，由平台分发给观众 |

拉流和推流用的是**同一组来源参数**，学会一次两边通用。

## 选画面和声音

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `video` | `mcu` / `user` / `none`，必填 | `mcu` 房间合成画面；`user` 某个人的画面；`none` 不要画面 |
| `video_uid` | uid | `video=user` 时必填 |
| `video_desc` | 轨道描述 | 这个人同时发布多路视频（如摄像头和屏幕共享）时指定其中一路，不传取先到的那一路 |
| `audio` | `auto`（默认）/ `mix` / `user` / `none` | `mix` 房间混音；`user` 某个人的声音；`none` 不要声音 |
| `audio_uid` | uid | `audio=user` 时必填 |
| `audio_desc` | 轨道描述 | 这个人发布多路音频时指定其中一路，不传取第一路 |

`audio=auto` 表示**声音跟随画面**：

| `video` | `auto` 解析为 |
| --- | --- |
| `mcu` | 房间混音 |
| `user` | 画面那个人本人的声音（`audio_desc` 仍可指定哪一路） |
| `none` | 不允许，报参数错误 —— 不要画面时必须明确说声音取哪里 |

`video` 和 `audio` 不能同时是 `none`。画面和声音可以来自不同的人，常见组合：

| 想要 | 参数 |
| --- | --- |
| 整个房间的合成画面和混音（直播） | `video=mcu` |
| 某个人的画面和声音（单路流，如监控某个终端） | `video=user`、`video_uid=A` |
| 主讲人画面 + 房间混音（观众能听到提问） | `video=user`、`video_uid=主讲人`、`audio=mix` |
| 某人的屏幕共享 + 他的麦克风 | `video=user`、`video_uid=A`、`video_desc=screen` |
| 合成画面，但不要声音 | `video=mcu`、`audio=none` |
| 只要房间混音（如交给转写服务） | `video=none`、`audio=mix` |
| 只要某个人的声音 | `video=none`、`audio=user`、`audio_uid=A` |

## 合成画面和混音依赖合流任务

`video=mcu`，或声音取到房间混音（`audio=mix`，或 `auto` 跟随合成画面）时，
频道里必须有一个**进行中的合流任务**——[启动录制/合流任务](/zh/rtc/server-api/mcu)时 `task_type` 带 `2`。
合成画面的布局、水印、成员名标签都在那里配，媒体输出只引用它的结果，见[云录制与合流接入指南](/zh/rtc/server-api/guides/recording)。

没有合流任务时，拉流和推流的表现不同：

| | 拉流 | 推流 |
| --- | --- | --- |
| 行为 | 直接返回错误码 `1073`，不签发一个拉不到东西的地址 | 允许先建，推流状态停在 `waiting`，合流任务开起来后自动开推 |
| 原因 | 地址签发出去就脱离我们的控制，拉不到只会让拉流端白等 | 符合「先配好推流、再开会」的习惯 |

只用单人画面和单人声音（`video=user`、`audio=auto` 或 `user`）时不依赖合流任务，也不占 MCU 资源。

## 拉流：HTTP-FLV 与 RTSP

|  | HTTP-FLV（`protocol=flv`） | RTSP（`protocol=rtsp`） |
| --- | --- | --- |
| 视频 | 只支持 H264，不转码。发布端用 VP8 时**拉不到画面**（拉流端收到 404） | 原样直通，H264、H265、VP8 都可以；VP8 / H265 要拉流端支持（ffmpeg、VLC 可以，很多 NVR 不行） |
| 音频 | Opus 转成 AAC（48k 单声道） | 默认转成 AAC；传 `rtsp_audio=opus` 原样直通 Opus，省去服务端转码 |
| 传输 | HTTP | 只支持 RTSP over TCP（如 ffplay 加 `-rtsp_transport tcp`） |
| 典型拉流端 | 网页（flv.js、mpegts.js）、ffmpeg | NVR、监控平台、VLC、ffmpeg |

+ **合成画面恒为 H264**，用 `video=mcu` 的 HTTP-FLV 不受发布端编码影响。要拉单人画面的 HTTP-FLV，请让发布端使用 H264
+ RTSP 默认 AAC 是为了兼容：NVR、监控平台和大多数 RTSP 客户端只认 AAC / G.711，不认 Opus。确认拉流端支持 Opus 时用 `rtsp_audio=opus`
+ 地址自带签名，默认 24 小时有效（`expire` 可调，最长一天），有效期内可被多个拉流端反复拉取；过期后新的拉流请求被拒，**正在播的不断**。
  实际有效期以返回的 `expire_at` 为准，播放前重新申请一次即可，不要长期缓存
+ **按需订阅**：有人来拉时才订阅，最后一个拉流端断开后自动退订，不拉不占资源，也没有停止接口
+ 地址可以提前生成：拉流时来源还没发布，拉流端会收到 404，需要重试；用户中途离开再回来，拉流不断，中间是一段空白
+ RTSP 不补静音：声音来源缺席（没发布、静音停发）时音频是一段空白，拉流端一般能正常处理

### 纯音频（`video=none`）的局限

纯音频 HTTP-FLV 没有画面时间轴，**声音来源断档时不补静音**：来源停发超过 3 秒，FLV 里的音频就断档，
网页播放器可能停在缓冲，来源回来后接上（连接不会断开）。需要连续不断的音频时，用 RTSP，或带上画面。

## 推流任务

推流是独立的任务：[开始推流](/zh/rtc/server-api/stream#开始推流)返回 `push_id`，
用它[停止推流](/zh/rtc/server-api/stream#停止推流)、[查推流状态](/zh/rtc/server-api/stream#推流任务列表)。

+ **一个频道可以同时推多路**：比如合成画面推视频号，同时把某位嘉宾的单人画面推到另一个平台
+ **同一频道对同一推流地址重复开始不会另起一路**：来源不变时直接返回已有的 `push_id`，来源变了就按新来源更新这一路 —— 所以想换画面不用先停再开
+ 推流地址支持 `rtmp://` 与 `rtmps://`，必须带推流码（`rtmp://host/app/` 这类流名为空的地址返回 `1075`）
+ 频道须已开启；**频道销毁时其下全部推流自动停止**
+ 视频只推 H264、不转码（合成画面恒为 H264；推单人画面时请让发布端用 H264），音频 Opus 转成 AAC
+ 推流列表里的地址已脱敏（推流码换成 `***`），完整地址只有你自己保存的那份

### 推流状态

| `status` | 含义 |
| --- | --- |
| `waiting` | 等待来源：合流任务还没开、要推的人还没发布或暂时离开。**不算失败、不告警**，来源出现后自动开推 |
| `connecting` | 来源已到，正在连接直播平台 |
| `publishing` | 推流中 |
| `retrying` | 推往直播平台失败（连不上、被拒、中途断开），3 秒后自动重连，原因见 `err` |
| `stopped` | 已停止（调了停止接口，或频道已销毁） |

推流列表不传 `push_id` 时返回进行中的与最近一天内停止的推流。

### 纯音频推流

`video=none` 的推流协议上可行，但**很多直播平台要求必须有视频**，接不接纯音频以平台为准。
声音来源停发时没有画面时间轴补静音：10 秒内的停发是一段空白，超过 10 秒推流断开、回到 `waiting`，
来源回来后重新连平台，平台一般会当成新的一段直播。

### 推流失败告警

推流持续失败（一直处于 `retrying`，约 90 秒）时，经 [`mcu_alarm` 回调](/zh/rtc/server-api/guides/callbacks)通知一次：

+ **`task_type` 为 `0`** 表示这是推流告警，此时 **`task_id` 是 `push_id`**
+ `push_id` 与 MCU 任务 ID 格式相同，但不是 MCU 任务，**不要拿去调 `mcu/detail` 等 `mcu/*` 接口**
+ 告警不代表推流已停止，网关仍在重试；是否恢复以推流列表的 `status` 为准

`waiting` 永远不告警 —— 来源不在是业务上的正常状态，不是故障。

## 错误码

| 错误码 | 含义 | 处理 |
| --- | --- | --- |
| `1070` | 没有可用的流输出网关 | 拉流需要部署媒体网关并启用拉流模块，私有化部署找部署方确认 |
| `1071` | 流输出网关签发拉流地址失败 | 稍后重试，持续失败联系我们 |
| `1072` | 没有可用的直播推流网关 | 推流需要部署媒体网关并启用推流模块 |
| `1073` | 房间没有进行中的合成任务 | 先启动 `task_type` 带 `2` 的合流任务，或改用单人画面 / 单人声音 |
| `1074` | 推流任务不存在 | 检查 `push_id` |
| `1075` | 推流地址无效 | 用 `rtmp://` 或 `rtmps://`，并带上推流码 |
| `1076` | 直播推流网关拒绝了推流请求 | 稍后重试，持续失败联系我们 |

全部错误码见[错误码](/zh/rtc/server-api/error-codes)。

## 私有化部署

媒体输出由媒体网关承担，要单独部署并放行拉流端口（RTSP 8554、HTTP-FLV 8556）、
放通到直播平台的出向访问（RTMP 1935 / RTMPS 443），见[网络与端口要求](/zh/product/deploy/ports)。

## 从旧接口迁移

旧的单路流、直播接口已删除，没有兼容期，升级前请把调用方改到新接口：

| 旧用法 | 新用法 |
| --- | --- |
| `stream/flv-url`（`uid`、`desc`、`audio`…） | `stream/pull-url`，`protocol=flv`、`video=user`、`video_uid=原 uid`、`video_desc=原 desc`；声音参数照旧语义改成 `audio` / `audio_uid` / `audio_desc` |
| `stream/rtsp-url` | `stream/pull-url`，`protocol=rtsp`、`video=user`、`video_uid=原 uid`。注意音频**默认改成 AAC**，要保持原来的 Opus 直通传 `rtsp_audio=opus` |
| `mcu/live-url` | `stream/pull-url`，`protocol=flv`、`video=mcu`（不再需要 `task_id`，按 `channel` 取） |
| `mcu/start` 的 `layout_data.push_url` / `push_audio*` | `stream/push/start`，`video=mcu`，`audio` 等同原 `push_audio`；停推用 `stream/push/stop`，不再跟着 MCU 任务停 |
| `task_type` 含 `8`（直播流） | 改成 `2`（合流），如 `9` → `3`；传 `8` 会报错。合流任务把合成画面发布回频道，再用上面的接口拉流或推流 |

+ 错误码 `1047`（MCU 推流地址无效）已删除，由 `1075` 取代；`1048`（推流模式的任务没有拉流地址）已删除，推流与拉流互不影响，不再有这种情况
+ 升级时还在进行中的类型 8 任务会自动按合流处理，已结束的历史任务查询时 `task_type` 仍可能含 `8`
+ 推流告警的 `mcu_alarm` 回调新增 `task_type=0` 的情况，按 `task_type` 区分 MCU 任务告警和推流告警
